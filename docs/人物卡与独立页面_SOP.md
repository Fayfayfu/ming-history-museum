# 人物卡与独立页面 SOP

版本：2026-08-23
适用范围：步入大明·人物馆的新增人物、已有卡片重写、独立页面扩建与关联数据补齐。

## 1. 目标与底线

人物馆不是名人简介库。每一张卡要让不了解明史的成年读者看明白：这个人是谁、处于哪一朝哪一段局势、做过什么、行动受什么条件限制、后果与评价为何有争议。

必须同时做到：

- **可读**：不默认读者知道年号、官制、事件前因或人物关系；首次出现的关键背景须解释。
- **可核**：关键年代、任职、事件、作品、处分与引文均有可打开的来源入口。
- **有边界**：区分可考史实、合理推演与艺术想象；不得把心理、密谈、动机或传说写成事实。
- **不模板化**：人物的展示重点由其历史角色决定。制度人物重制度与决策链，军事人物重战场条件与组织，文化人物重作品及其传播，皇帝重统治与权力结构。
- **不脸谱化**：不以“忠臣 / 奸臣 / 明君 / 昏君”代替过程与责任分析。

## 2. 先判定：是否值得做正式人物卡

新增前先回答四个问题：

1. **是否有足够证据密度？** 至少能支撑基本身份、关键时段、三至六个行动节点、结局或影响。
2. **是否有明确的策展价值？** 能补足人物、制度、事件或空间关系中的一个缺口，而非仅为凑名录。
3. **应做人物卡还是事件节点？** 若一个人只在单一事件中有明确作用，优先补事件关联；不要把一条名言或一次亮相硬扩写成人生传记。
4. **是否要做独立页？** 有连续人生转折、足够史料、至少六个可解释节点的人，才进入独立页面。

结论分为：

- 正式人物卡；
- 正式人物卡 + 独立页面；
- 只补事件 / 机构 / 关系节点；
- 暂缓，写入 `data/ming_historical_slices_batch9.json` 的 `meta.deferred`，说明材料缺口。

## 3. 研究顺序与证据分级

### 3.1 最小研究闭环

1. 先读《明史》本纪、列传、宰辅年表或职官志，形成待验证的问题，不把它当作唯一答案。
2. 优先回到《明实录》、奏疏、文集、地方志、馆藏目录、墓志或可核验的专业数据库补关键缺口。
3. 对重大争议至少记录：哪些事实可确认、哪些只是当时指控、哪些是后世归因、哪些仍不确定。
4. 对文化人物，补作品本身、版本或馆藏入口；不能只写“著有很多作品”。

### 3.2 来源优先级

1. 原始 / 同时代材料：实录、奏疏、文集、碑刻、官修制度文献。
2. 正史与年表：《明史》本纪、列传、职官志、宰辅年表。
3. 第一方机构：故宫、国家图书馆、国家级博物馆、大学或研究机构数据库。
4. 学术研究、可靠工具书。
5. 维基百科仅可作导航；不得作为争议结论的唯一依据。

### 3.3 置信度写法

- **高**：年代、任职、原文或馆藏信息可直接核对。
- **中**：事实主干可信，但动机、责任比例、具体经过或版本仍有分歧。
- **低 / 未知**：仅有晚出材料、传说、无法核验的图像或信息缺口。

不要写“高；生年中”这类非标准字段；总体字段只能使用 `高 / 中 / 低 / 未知`，细分要写进说明。

## 4. 正式人物卡的数据要求

主卡写入 `data/ming_core.json`。必填字段：

```json
{
  "category": "文臣 / 武官 / 皇帝等",
  "name": "姓名",
  "birth": 0,
  "death": 0,
  "office": "最能说明其位置的职务",
  "office_start": 0,
  "office_end": 0,
  "hometown": "籍贯或保守说明",
  "summary": "可读的一句生涯概括",
  "evaluation": "贡献、代价与争议边界",
  "confidence": "高 / 中 / 低 / 未知",
  "source1": "具体来源 URL",
  "source2": "第二条具体来源 URL",
  "notes": "年份、争议、口径说明",
  "domains": ["历史领域"]
}
```

### 4.1 文案要求

- `summary` 先说行动与位置，不堆叠爵位。
- `evaluation` 至少同时包含贡献和代价；负面人物也使用“主要行动与后果”，不使用预设褒贬标签。
- 关键任期必须让读者看到**对应皇帝 / 朝次 / 年号**。一年内的任期也不能漏掉皇帝信息。
- 身份栏列最关键的二至三项职务；避免把完整仕履塞进一行。
- 生年、卒年、籍贯不确定时写“待考”或说明分歧，不能补一个看似精确的数字。

### 4.2 必须同步的关联数据

新增正式卡后，逐项检查：

- `data/ming_people_timeline.json`：新增时间锚点、依据、来源编号、角色与大小。
- `data/ming_person_institutions.json`：仅添加可核验的任职、兼任、掌理、创设或制度塑造关系；写明期间、年份、说明和来源。
- `data/ming_events.json`：补已有事件的 `people` 映射；若重要节点不存在，可新建事件。不得把人物硬挂到其去世后或时间不重合的事件。
- 独立页中的 `relatedEvents` 必须使用事件馆的**精确标题**，否则链接会失效或搜不到。
- 历史切片未完成时，同步更新 `meta.deferred`，以保证审校口径一致。

## 5. 人物速览（抽屉）要求

人物抽屉不是缩小版百科条目，而是读者进入人物的一条清晰路径。

数据写入 `data/ming_person_pages*.json` 的人物对象；抽屉自动读取独立页的 `heroQuestion`、`lead` 和 `scenes`。

### 5.1 必备结构

1. **问题式标题 `heroQuestion`**：指出这个人的核心历史困境，不用空泛赞词。
2. **概括 `lead`**：约一段，交代身份、时代、转折和后果。
3. **六条速览 `scenes`**：
   - 左侧：公历年份 / 时段；
   - 第二行：年号与皇帝；
   - 右侧：加粗标题 + 14px 左右的解释性摘要；
   - 每条都回答“发生了什么、为什么发生、改变了什么”。

### 5.2 写法禁区

不要使用“出生与出身 / 进入历史现场 / 主要行动与位置 / 结局与影响”这种所有人物通用的空模板。标题应当是这个人独有的行动或困境，例如：

- “他两次做到右丞相，却无法让中书省脱离同僚与皇权的夹击”；
- “一个能治河的人，为什么参与了宫门政变”；
- “首辅推动立储，却在折中方案里失去公议”。

## 6. 独立页面要求

### 6.1 何时制作

人物已有完整、连续、可核的行动链时，人物卡与独立页必须同步更新。独立页不是把卡片扩写成更多形容词，而是让读者沿时间、制度和证据进入其一生。

### 6.2 最小结构

每个独立页必须包含：

- `slug`、主题、`readingMode: "clear-biography"`；
- `eyebrow`、`heroQuestion`、`lead`、`thesis`；
- **六幕 `scenes`**；
- `relatedEvents`；
- 至少三条 `sources`；
- 结尾的 `finalQuestion`。

每幕必须有：

```json
{
  "year": "公历时段",
  "reignYears": "明 · 皇帝 / 年号",
  "age": "年龄或保守说明",
  "kicker": "第几幕及独有提示",
  "title": "具体、可读的转折标题",
  "preview": "供人物速览显示的短摘要",
  "body": ["第一段：事实与背景", "第二段：条件、后果与边界"],
  "evidenceNote": "本幕依据",
  "confidence": "高 / 中 / 低",
  "interpretationBoundary": "哪些是解释，哪些不能推出",
  "primarySource": {
    "title": "原文主题",
    "location": "卷次、纪年或段落定位",
    "original": ["短原文"],
    "reading": "这段原文能确认什么",
    "boundary": "这段原文不能确认什么",
    "url": "可打开的具体 URL",
    "confidence": "高 / 中 / 低"
  }
}
```

### 6.3 六幕的设计原则

六幕不是机械的“出生—入仕—功业—结局”。应围绕人物的真实转折组织，例如：

- 起点与进入哪一种制度位置；
- 第一次关键选择；
- 资源、组织或知识如何形成；
- 权力、战争、制度或作品的核心转折；
- 代价、失败或争议；
- 结局、身后影响与后世记忆的边界。

每段正文应足以独立解释，不依赖读者预先知道事件背景。不要补写未经记载的对话、脸部表情、内心独白或“他当时一定认为”。

## 7. 作品、画像与视觉材料

作品型人物展厅的完整界面与数据规范见 [`.interface-design/system.md`](../.interface-design/system.md)。该规范是项目级合同，不是单批次视觉说明。

### 7.1 作品

- 以文化、思想、医学、科技、书画或著述闻名的人物，作品不是附录，应成为页面的展示重点。
- 展示题名、原文 / 图像 / 馆藏入口、版本或署名边界。
- 不把流行名句自动当作本人自述，也不把后世选本的传播等同于作者原意。

### 7.2 何时启用作品型展厅

大型作品画廊不是文化人物的默认模块。必须同时满足：

1. 可视觉展陈的书画或图像作品，是解释人物历史位置的主要证据；
2. 至少两件作品的作者归属、馆藏入口、图像许可与本地资产可核验；
3. 独立页明确使用 `feature.type: "gallery"` 或 `creativeGallery: true` 显式启用；
4. 每件作品声明 `display: "panorama" / "landscape" / "portrait"`，并完整显示、不裁切。
5. 每张实际展示的作品图提供“查看大图”按钮；桌面支持双击，移动端支持单击，全屏后直接提供1倍、2倍、4倍、8倍，可拖动、复位并用 `Esc` 退出。长卷页面只保留一次完整总览，不重复输出内嵌细节图。

只有一件代表作时使用普通“作品证据”模块；以著述、兵书、诗文或知识体系为主时，使用文本、知识结构或训练系统，不为统一视觉强行套用画廊。

作品数据统一写入 `data/ming_creative_works.json`。至少包含题名、年代、媒材、画幅类型、本地图片、具体馆藏页、馆藏机构、许可、置信度和有解释边界的策展解读。

### 7.3 画像

先找人物、年代、来源与许可都可核验的馆藏或公版图像。不能把影视剧照、来源不明网图、纪念雕像直接称为“人物画像”。

若无可靠图像，可用 AI 想象像，但必须：

- 在 `data/ming_portraits.json` 标为 `status: "imagined"`、`portraitKind: "AI想象像"`、`confidence: "未知"`；
- 写明历史锚点与艺术想象边界；
- 画像注释必须明确“不代表真实相貌”；
- 原始 PNG 存 `data/media-originals/portraits/batch-N/`；
- 网站使用 4:5、720×900 左右的 WebP，存输出资产目录；
- 构建脚本必须负责从原图生成 WebP，不能仅手工放进输出目录。

## 9. 验收与发布

### 9.1 内容验收

- JSON 可解析；人物无重名；字段完整。
- 新人物至少两条具体来源链接；独立页每幕都有 `primarySource.url`。
- 六幕均有年号、标题、预览、两段正文、依据与解释边界。
- 事件、机构、年表、卡片和独立页中的姓名、年份、职务一致。
- 画像文件存在、可读、标识与元数据一致。

### 9.2 技术验收

```bash
npm run build:museum
npm run verify:people-timeline
npm run audit:museum
npm run build:deploy
npm run verify:deploy
git diff --check
```

若 `audit:museum` 失败，先区分：是本轮引入的结构错误，还是已存在的遗留数据错误；不得把未解决错误写成通过。

### 9.3 部署纪律

1. `git status` 确认只暂存本轮相关文件；不混入临时截图、锁文件、密钥、无关文档或其他代理的未跟踪文件。
2. 提交、推送主分支。
3. 先执行 `npm run build:deploy`，部署**构建后的 `dist`**。
4. 不要用 Vercel CLI 直接上传仓库根目录；根目录会把原图、研究资料和无关文件一并上传。
5. 发布后核对生产别名、关键人物页、图片加载和移动端布局。

## 10. 最终检查表

- [ ] 这个人值得独立成卡，而不只是一个事件节点。
- [ ] 普通成年读者不查资料也能读懂其核心经历。
- [ ] 没有把首辅、丞相、总督、巡抚等不同制度位置混为一谈。
- [ ] 年份、年号、皇帝和任期都能对上。
- [ ] 史实、解释、指控、传说和艺术想象已分层。
- [ ] 负面信息没有被粉饰；争议信息没有被写成既定事实。
- [ ] 文化人物的作品得到与其身份相称的展示。
- [ ] 机构与事件关系既不漏，也不跨越人物实际活动时间。
- [ ] 画像来源、权利、置信度和 AI 标识清楚。
- [ ] 抽屉速览、独立页、事件馆、制度馆和年表已同步。
- [ ] 构建、校验、部署包和生产页面均已检查。
