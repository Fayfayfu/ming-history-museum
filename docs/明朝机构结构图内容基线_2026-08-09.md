# 《明朝机构结构图内容基线》

- 文档版本：v0.2
- 日期：2026-08-09
- 适用产品：步入大明｜数字历史博物馆
- 文档状态：P0内容基线已固化；结构数据v0.1已生成并通过专项校验
- 本版范围：明朝中央中枢、行政、监察司法、内廷厂卫、军事、地方六个系统
- 总体置信度：中高

## 1. 文档目的

本文件定义“明朝机构结构图”的内容边界、时间切片、机构节点、关系类型、专题视图、文案规则、证据规则和验收标准。它是后续数据建模、信息架构、视觉设计与页面开发共同遵守的基线。

本文件不是《明史·职官志》的完整数字化，也不是一张固定不变的明朝官制总表。

结构图要帮助用户回答五个问题：

1. 一道奏章如何进入中枢并形成政令？
2. 谁负责行政，谁负责监察，谁负责复核？
3. 普通司法与厂卫诏狱有什么区别？
4. 兵部、五军都督府与实际统兵者如何分工？
5. 中央如何通过地方三司、巡抚和总督治理地方？

## 2. 核心判断

### 2.1 不能制作一张永久有效的上下级树

明代机构同时存在正式统属、奉旨办事、文书流转、监察封驳、司法复核、军事协同、临时差遣和皇帝直接授权等关系。若全部画成“上级管理下级”，会产生以下错误：

- 把内阁误写成六部的固定法定上级；
- 把司礼监误写成内阁的上级或下级；
- 把都察院与六科误并为一个机关；
- 把兵部与五军都督府误画成简单上下级；
- 把东厂与锦衣卫误画成始终稳定的隶属关系；
- 把巡抚、总督误写成从明初起即固定存在的省级行政长官；
- 把洪武前期的中书省结构延续到整个明代。

因此，产品采用：

> 一张总览图 + 五张专题图 + 时间切片 + 可核验的机构关系数据。

该判断置信度：高。

### 2.2 皇帝是权力中心，但不是所有流程中的唯一中转节点

明代制度改革持续强化皇帝对六部、军队和监察系统的直接控制。然而实际政务仍需要通政使司、内阁、司礼监、六科、六部等机构完成递送、拟议、批答、封驳与执行。

图中应同时表现：

- 皇帝的最终裁决与直接授权；
- 机构之间的常规政务流程；
- 皇帝越过常规流程直接处置的特殊路径。

该判断置信度：高。

### 2.3 制度地位与实际权势必须分开

内阁、司礼监、东厂、锦衣卫等机构或职位的实际权势，会随皇帝、掌权人物和政治环境发生变化。产品不得把某一时期的权势关系写成整个明代的法定关系。

例如：

- 内阁并非自永乐初年起就稳定节制六部；
- 司礼监批红在正统以后趋于制度化，不能反推到洪武前期；
- 厂强卫附、卫强凌厂都曾出现，厂卫之间不存在贯穿明代的单一权力排序；
- 西厂只在成化、正德的特定时段存在。

该判断置信度：高。

## 3. 史实与证据规则

### 3.1 内容层级

| 层级 | 定义 | 产品处理 |
|---|---|---|
| 可考史实 | 有原典、会典、实录、正史职官志或专业机构材料支持 | 可作为节点、关系和正文陈述 |
| 解释 | 对制度功能、制衡机制和政治影响的概括 | 必须写明“意味着什么”，不得冒充原文 |
| 合理推断 | 根据多个事实推导出的运行判断 | 明确标记“可理解为”“典型情况下” |
| 艺术想象 | 为叙事、场景或视觉表达增加的非史料细节 | 不进入结构图基线；如未来使用，必须单独标记 |

### 3.2 置信度

| 等级 | 判定标准 |
|---|---|
| 高 | 至少有一条原典或制度文献支持，并有专业机构或可靠研究交叉印证；不存在影响产品表达的重大争议 |
| 中 | 基本事实可靠，但起止时间、权限边界或实际运行存在阶段差异；产品必须附限制说明 |
| 低 | 只有单一二手材料、通识性概括或存在明显争议；不得进入默认总览图 |
| 未知 | 当前未完成核验；不得作为事实发布 |

### 3.3 来源优先级

1. 《明实录》《大明会典》《明史》职官志、兵志、刑法志等原典；
2. 故宫博物院、中国社会科学院等专业机构资料；
3. 有明确作者、出处和论证的学术论文、专著；
4. 地方政府与地方志资料，用于地方制度实例；
5. 通识百科仅作检索入口，不独立支撑争议性结论。

### 3.4 关系证据要求

机构节点存在，不等于两个机构之间存在稳定关系。每一条关系必须单独记录：

- 关系双方；
- 关系类型；
- 方向；
- 适用时期；
- 是否属于常规制度或特殊路径；
- 说明；
- 来源；
- 置信度。

## 4. 产品范围

### 4.1 P0范围

- 4个宏观制度时间切片，并支持切片内关键年份状态；
- 29个规范节点（总览默认折叠六部与三法司）；
- 6个系统分组；
- 7类关系；
- 1张总览图；
- 5张问题型专题图；
- 机构详情卡；
- 关联现有人物卡与事件卡；
- 桌面端关系图；
- 移动端纵向流程叙事。

### 4.2 P1范围

- 将中晚明继续细分为正统—天顺、成化—弘治、正德、嘉靖—隆庆、万历、天启—崇祯；
- 两个时期并排比较；
- 南京留都机构体系；
- 翰林院、詹事府、宗人府、太常寺等扩展节点；
- 十二监、四司、八局完整内廷结构；
- 京营演变、九边、营兵与卫所军关系；
- 从具体事件播放制度路径；
- 将人物任职变化映射到机构权力变化。

### 4.3 明确不做

- 不收录明代全部官署；
- 不制作一张跨越276年的永久组织树；
- 不把古代机构对应为现代国务院、最高法院、国防部、纪委或情报机关；
- 不制作没有史料依据的机构“权力值”；
- 不以官阶高低代替真实制度关系；
- 不将实际影响力直接写成法定统属；
- 不把《明朝那些事儿》的文学评价作为制度事实来源。

## 5. 时间切片

时间切片是产品解释工具，不等同于学界唯一的制度分期。P0采用“4个宏观切片 + 选中年份状态”两级时间模型：宏观切片负责解释制度断点，节点是否显示则由选中年份和 `active_periods` 决定。

| ID | 产品名称 | 时间 | 结构图关键变化 | 置信度 |
|---|---|---:|---|---|
| `early_hongwu` | 洪武前期：中书省统政 | 1368—1379 | 中央保留中书省和丞相；六部处于中书省体系；地方行省在1376年后改为三司 | 高 |
| `late_hongwu_jianwen` | 洪武后期至建文：皇帝直辖六部 | 1380—1402 | 罢中书省、废丞相；六部直接对皇帝负责；五军都督府、都察院、锦衣卫等陆续形成 | 高 |
| `yongle_xuande` | 永乐至宣德：内阁与内廷机制形成 | 1403—1435 | 内阁逐渐形成；东厂于1420年设置；司礼监地位在宣德朝上升 | 高 |
| `mid_late_ming` | 正统至崇祯：监阁、厂卫与督抚体系展开 | 1436—1644 | 票拟、批红运行更成熟；巡抚总督逐渐常态化；厂卫权势随时期变化；西厂仅分段出现 | 中高 |

各宏观切片默认年份：

| 宏观切片 | 默认年份 | 可选关键年份 |
|---|---:|---|
| 洪武前期 | 1370 | 1376、1379 |
| 洪武后期至建文 | 1390 | 1380、1382、1395、1402 |
| 永乐至宣德 | 1425 | 1403、1420、1429、1435 |
| 正统至崇祯 | 1600 | 1442、1477、1482、1506、1510、1572、1621、1627、1644 |

年份状态规则：

- 年份区间按公历年包含首尾年；若制度变化发生在年内，选中该年时显示“本年发生变化”状态，并以变化后的结构作为年度主图；
- 精确到月或日的变化写入详情卡，不强迫总览图表现同一年内的多次开闭；
- `active_periods` 已确认时，节点按年份显示或隐藏；
- 只确认“某几年间反复设置”而未确认全部月份时，节点显示为“阶段内反复设置”，不得显示为稳定常设；
- 宏观切片不直接决定节点存在状态，因此西厂可以在同一宏观切片内随选中年份出现、消失或标为“反复设置”。

### 5.1 必须可见的时间变化

1. 选中1368—1379年：显示中书省、丞相，六部与中书省相连。
2. 选中1380年及以后：中书省、丞相退出，六部直接连接皇帝；1380年详情注明改革发生于洪武十三年正月。
3. 切换到永乐以后：显示内阁；其关系标注为辅政、票拟，不标注为统辖六部。
4. 切换到1420年后：显示东厂。
5. 切换到正统以后：显示司礼监批红关系。
6. 西厂按独立活动区间显示，不覆盖整个中晚明。

### 5.2 西厂的特殊时间规则

西厂使用可重复活动区间或“区间内反复设置”状态，不使用一个连续、稳定的起止年份：

- 成化十三年至成化十八年，即1477—1482年间两度开设，不能视为不间断连续存在；
- 正德初年重开，至正德五年，即约1506—1510。

两段内部的精确开闭月份，本版不写入面向用户的正文；进入机器数据前继续核对《明实录》或《大明会典》。在完成核对前，1477—1482年选择任一年时统一显示“成化年间反复设置”，不得伪造逐年开闭状态。

该条总体置信度：中高。

### 7.7 节点口径

以上六表合计29个规范节点，是P0唯一可进入关系数据的端点清单。其中：

- “六部”“三法司”是结构组节点；
- 吏、户、礼、兵、刑、工六部是可展开的机构节点；
- 十三道监察御史、巡按御史、北镇抚司、京营、边镇、总兵等在P0只作为机构详情中的职位、属官、军事空间或专题叙事标签，不单独进入总览关系图；京营、边镇与总兵待P1完成制度沿革与来源补证后再升格为节点；
- “百司”“内廷”“军事执行体系”“地方司法事务”等抽象词不是节点；
- P0关系表的 `from`、`to` 只能使用本节29个规范ID；
- 如专题必须让新实体成为可连线端点，必须先将其补入节点表并重新计数。

默认总览可见数低于29：六部默认折叠为1个组节点，三法司默认作为分组容器而非额外可见方框，失效节点按选中年份隐藏。

## 10. 五张专题图内容基线

### 10.1 专题一：一道奏章如何变成命令

用户问题：官员递交的奏章经过谁，谁提出意见，谁作出最终决定，谁负责执行？

默认采用“正统以后典型流程”：

1. 京内外官员或有关衙门形成题奏；
2. 通政使司承担递送、汇达等职能；
3. 奏章进入皇帝与内廷处理范围；
4. 需要拟议者交内阁票拟；
5. 皇帝作出裁决；
6. 在正统以后的典型代批机制下，司礼监按皇帝意旨照票批红；皇帝也可亲自批答或改动票拟；
7. 文书发出并交六科、六部或有关衙门承办；
8. 六科可抄发、稽察、封驳有关事项。

必须显示的例外：

- 皇帝亲自批答；
- 奏章留中不发；
- 内阁票拟被改票；
- 特旨越过常规拟议与承办路径；
- 不同文书类型的流转方式并不完全相同。

专题结论：票拟是处理意见草案，批红也不等于司礼监拥有独立最终决策权。

本专题置信度：中高。

### 10.2 专题二：谁来监督官员

核心节点：皇帝、都察院、十三道监察御史、六科、六部、巡按御史、提刑按察使司、吏部。

核心区别：

| 体系 | 重点 |
|---|---|
| 都察院、监察御史 | 纠劾百司、巡按地方、监察官邪 |
| 六科给事中 | 对应六部稽察，参与规谏、封驳、抄发等 |
| 吏部 | 官员选授、考核、升降 |
| 提刑按察使司 | 地方刑名、监察 |

必须提示：六科与都察院官员常合称“科道”，但六科不是都察院下属。

本专题置信度：高。

### 10.3 专题三：三法司与厂卫诏狱

常规司法路径：

> 地方审理或中央问拟 → 刑部受理、审拟 → 都察院纠察或参与会审 → 大理寺复核、驳正 → 重大案件奏请皇帝裁决

特殊厂卫路径：

> 皇帝或受宠内廷权力中心授权 → 东厂、锦衣卫侦缉 → 北镇抚司审讯或诏狱 → 移送法司拟罪、会审，或出现越过常规司法的奉旨处置

必须提示：

- 锦衣卫同时有侍卫、仪仗、亲军职能；
- 东厂无完整独立官僚司法体系，执行人员和审讯环节与锦衣卫关系密切；
- 厂卫所获案件并非全部合法地绕过三法司；
- 实际政治迫害与法定制度边界之间存在张力；
- 厂与卫的权势排序随时期变化。

首批关联人物：蒋瓛、纪纲、钱宁、陆炳、田尔耕、魏忠贤、汪直、刘瑾。

本专题置信度：高。

### 10.4 专题四：明朝由谁调兵

核心规范节点：皇帝、兵部、五军都督府、都指挥使司、卫所、巡抚、总督。京营、边镇、总兵在P0只作为解释战时统兵与边防空间的叙事标签，不作为连线端点。

必须分开的四种事务：

1. 军令与调遣；
2. 武官选授与军政；
3. 军籍、卫所与日常管理；
4. 战时实际统兵。

基础关系：

- 皇帝保留最终调兵与重大军事裁决；
- 兵部掌军令、武官选授等军政事务；
- 五军都督府分领都司、卫所，掌军籍与有关军政；
- 战时可临时命将充总兵官，统领调发军队；
- 中后期巡抚、总督参与跨区域军政协调，但职权来自具体敕令。

必须提示：明代军事制度在中后期出现卫所衰变、营兵发展、督抚权重变化，P0只展示基本骨架。

本专题置信度：中高。

### 10.5 专题五：中央如何控制地方

核心节点：六部、都察院、五军都督府、承宣布政使司、提刑按察使司、都指挥使司、巡抚、总督、府、州、县、卫所。

默认结构：

- 承宣布政使司：民政、财政等；
- 提刑按察使司：刑名、监察等；
- 都指挥使司：地方军事、卫所；
- 三司互不统属，各有上达中央的制度关系；
- 府、州、县构成地方行政层级；
- 巡抚、总督以差遣和兼衔协调跨系统、跨区域事务，后来逐渐常态化。

必须提示：

- 三司辖区并非在所有地区完全重合；
- 两京、直隶地区与普通布政使司地区不同；
- 土司、都司实土卫所、边疆羁縻等特殊制度不在P0展开；
- 巡抚、总督不能直接翻译为现代省长或总督区行政长官。

本专题置信度：中高。

## 11. 机构详情卡字段

每个机构详情卡必须包含：

| 字段 | 必填 | 说明 |
|---|---:|---|
| `id` | 是 | 稳定英文ID |
| `name` | 是 | 正式中文名称 |
| `aliases` | 否 | 简称、别称 |
| `system` | 是 | 所属系统 |
| `active_periods` | 是 | 可包含多个非连续区间 |
| `status_by_phase` | 是 | 各时间切片中的存在与功能状态 |
| `summary` | 是 | 40—80字核心职掌 |
| `core_functions` | 是 | 3—5项，不用现代机构名替代 |
| `not_equivalent_to` | 是 | 明确不应类比为什么现代机构 |
| `relations` | 是 | 指向关系表ID |
| `people` | 否 | 关联正式人物卡，并标注关联类型 |
| `events` | 否 | 关联事件卡 |
| `sources` | 是 | 原典和专业机构入口 |
| `confidence` | 是 | 高／中／低／未知 |
| `review_notes` | 否 | 争议、待核和版本说明 |

### 11.1 人物关联类型

沿用并扩展现有 `data/ming_person_institutions.json`：

| 关系 | 定义 |
|---|---|
| 任职 | 人物拥有可核验的正式职衔或实际任职 |
| 提督 | 奉命统领厂卫等特定机构 |
| 创设 | 君主直接创设、恢复或重组机构 |
| 制度塑造 | 对机构权力结构有直接、可识别的影响 |
| 奉差 | 以临时差遣、兼衔处理相关事务 |
| 被侦办 | 被该机构调查、逮捕或审讯；不得误写为任职 |
| 制度冲突 | 与机构发生具有制度意义的冲突；不得误写为隶属 |

“被侦办”和“制度冲突”只用于详情关联，不参与人物馆的任职筛选。

## 12. 建议数据结构

建议新增 `data/ming_institution_graph.json`，不要直接把现有“人物—机构关联”数据扩写成结构图。

```json
{
  "meta": {
    "version": "0.1",
    "scope": "P0明朝机构关系图",
    "updated_at": "2026-08-09"
  },
  "phases": [],
  "systems": [],
  "institutions": [],
  "relations": [],
  "views": [],
  "sources": []
}
```

机构示例：

```json
{
  "id": "western_depot",
  "name": "西厂",
  "system": "inner_court_surveillance",
  "active_periods": [
    {
      "start": 1477,
      "end": 1482,
      "state": "intermittent",
      "exact_intervals_verified": false,
      "confidence": "中高"
    },
    {
      "start": 1506,
      "end": 1510,
      "state": "reopened",
      "exact_intervals_verified": false,
      "confidence": "中"
    }
  ],
  "summary": "成化年间反复开设、正德初年重开的侦缉机构。",
  "not_equivalent_to": ["贯穿明代的常设情报机构"],
  "confidence": "中高",
  "source_ids": ["dpm_western_depot", "mingshi_95"]
}
```

关系示例：

```json
{
  "id": "rel_cabinet_draft_response",
  "from": "grand_secretariat",
  "to": "emperor",
  "type": "document_flow",
  "label": "票拟",
  "active_periods": [
    { "start": 1425, "end": 1644, "precision": "approximate" }
  ],
  "is_typical_flow": true,
  "note": "票拟是供皇帝裁决的批答草案，不等于内阁拥有最终决策权。",
  "confidence": "中高",
  "source_ids": ["dpm_draft_rescript"]
}
```

数据规则：

- 一个机构可有多个 `active_periods`；
- 一个关系也可有多个 `active_periods`；
- 机构存在不代表某项职能始终存在；
- 年份不精确时必须记录 `precision`；
- 每一条关系独立标注置信度；
- 叙事流程与机器关系分开存储；
- 任何带“典型”“通常”的流程都要保留例外说明。

## 14. 当前产品映射

现有 `data/ming_person_institutions.json` 已有12个机构实体：

当前产品映射置信度：高，发布前需重新运行本地构建与验证确认数量。
